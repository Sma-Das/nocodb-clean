# Independent verification of the two performance edits

## Scope and conclusion

Reviewed the actual application diff and followed callers, filter compilation, cache helpers, and canvas event handling. Both edits are supported by the source and have no identified new correctness blocker. Count intentionally changes incorrect OR outcomes to agree with list; it is not behavior-equivalent to every old count. The frontend edit removes synchronous repeated work while preserving the first cache commit, request settlement, and detached comment request. No application files were edited and no tests were run by this verifier.

## Count filter grouping

- `packages/nocodb/src/services/datas.service.ts:292` parses explicit filters into `listArgs.filterArr`; `:300` attaches custom conditions; `:302` passes the same arguments into count and list concurrently. A separate count endpoint also parses `filterArrJson` before count at `:139`. These are real user-facing consumers of the changed path.
- `packages/nocodb/src/db/BaseModelSqlv2.ts:1135` retains RLS, `:1136` retains custom conditions, `:1144` retains view conditions, `:1151` retains the explicit filter group with `logical_op: 'and'`, and `:1156` retains the parsed `where` group. The no-view/ignore-view branch retains the corresponding groups at `:1170`, `:1171`, `:1179`, and `:1184`. The only removals are the second, ungrouped copies of explicit filters. This now matches list's structure at `:934`, `:951`, `:956`, and `:977`.
- `packages/nocodb/src/models/Filter.ts:130` preserves the supplied children through construction, and `:666` returns them directly. The retained wrapper therefore contains the complete original filter array, including its nested groups; removing the spread does not drop those predicates.
- `packages/nocodb/src/db/conditionV2.ts:119` maps each filter's `or` to `orWhere`, `and` to `andWhere`, and `not` to `whereNot`. The outer array invokes those methods at `:206`, and a nested group's children invoke them at `:248`. Thus duplication was not generally harmless: with mandatory restriction V and explicit A OR B, the old outer tree could behave as `(V AND (A OR B) AND A) OR B`. B could escape view/custom/RLS restrictions inside this filter tree. The new tree keeps `(V AND (A OR B))`. Soft-delete remains separately applied at `BaseModelSqlv2.ts:1125`; do not claim this specific OR escaped every separate QB restriction.
- Disabled array entries are removed at `conditionV2.ts:179`; disabled groups return a no-op at `:214`; disabled leaves return a no-op at `:257`. The retained wrapper goes through exactly those same checks. CE supportToggle is false at `models/Filter.ts:151`; testing toggle behavior requires a controlled true implementation/stub. Group disable must cover descendants as well as leaf disable.
- The CE RLS resolver is empty at `BaseModelSqlv2.ts:10631`; `getRlsConditions` supplies cloned results at `:10623`. The grouping argument is verifiable in CE with a stubbed resolver, but this review cannot claim a reproduced production EE authorization incident.
- List/count equivalence should be asserted under equivalent options. `DatasService.getDataList` currently hardcodes count's ignore-view option to false at `datas.service.ts:303` while list receives `ignoreViewFilterAndSort` at `:312`; list also exposes additional special options. That preexisting difference is outside this edit.

### Meaningful backend tests

1. Build a small actual SQL fixture containing: a row inside V matching A only; inside V matching B only; outside V matching B only; inside V matching neither. Apply `[A, { ...B, logical_op: 'or' }]` and assert count equals the unpaginated list and excludes the outside-V B row. Run with a view, without a view but with customConditions, and with a nonempty stubbed RLS group. Include a restrictive parsed `where` independently so its RHS cannot escape either. Assert expected IDs, not only equal lengths.
2. Repeat for all-AND, a leading OR, nested OR under NOT, empty/omitted explicit arrays, disabled false/0 leaf, disabled whole group, and all-disabled children with toggle support true. Confirm CE's false support leaves the enabled flag behavior unchanged. Confirm `ignoreViewFilterAndSort=true` drops the view but retains custom/RLS restrictions for both methods.
3. Use a real lookup/relation or formula predicate, assert returned count, and inspect generated SQL or instrument predicate compilation to establish one explicit predicate tree rather than two. Stubbed count results alone would not establish correct grouping. Include soft-deleted fixture rows so unrelated mandatory constraints remain enforced.

## Bulk cache pass removal

- `packages/nc-gui/composables/useInfiniteData.ts:605` checks staleness before processing each bulk response. The retained block formats each chunk (`:618`), upserts once (`:626`), marks it loaded (`:629`), invalidates displaced chunks (`:630`), collects rows for comments (`:632`), and settles the request (`:637`). Missing payloads reset chunk state at `:634`; per-chunk failures reject/reset at `:638`. All of this survives unchanged.
- `packages/nc-gui/utils/infiniteCacheUtils.ts:43` builds primary-key/index sets, `:49` scans the whole existing cache for displaced duplicates, and `:61` writes incoming rows. `invalidateChunksAt` changes only removed indices' other chunks at `:78`. Removing the second pass avoids that repeated scan/write; it leaves the authoritative first-pass duplicate removal and invalidation intact.
- `useInfiniteData.ts:443` maps IDs to the formatted Row objects, then awaits the comment call at `:467`. It writes counts to those same objects at `:475` and emits `TRIGGER_RE_RENDER` at `:482`. The caller retains the detached call at `:648`. The old second cache loop ran synchronously after starting that async function, before its awaited continuation could update counts. It therefore could not serve as a post-enrichment cache refresh. Promise `.then` consumers also resume after this synchronous processing completes; removing a second `resolve` does not remove a second consumer continuation because promises settle once.
- Be precise about reactivity: the helper holds formatted Row references and mutates them directly; it does not re-read rows through `getDataCache`. Thus the claim that it specifically "mutates through the reactive cache" is stronger than the implementation establishes. It does mutate the objects inserted into the cache. Canvas explicitly consumes the event and schedules a repaint at `packages/nc-gui/components/smartsheet/grid/canvas/composables/useCanvasTable.ts:2117`. Event-driven repaint remains unchanged. Template-only consumers may warrant separate reactive behavior validation, but the removed pre-await loop could not fix late count mutation.
- Existing safety limits remain: `useInfiniteData.ts:437` rejects replaced group cache refs only; root requests are never stale by that predicate. Queued stale groups are skipped at `:552`, in-flight stale responses at `:607`, aborted requests at `:653`, and stale fallback requests at `:671`. Requests capture cache refs at `:736`. This edit retains these guards; it adds no search-generation protection or comment-request cancellation.
- If a group/cache is replaced or a row is evicted/replaced while comments await, the helper can mutate detached old rows and emit a repaint. It cannot reinsert stale rows because it has no cache write after the await. Duplicate IDs across formatted chunks also map to only the last Row at `:459`. These are preexisting limitations, not regressions caused by removing the second pass.

### Meaningful frontend tests

1. Drive the composable's bulk path with two successful chunks and an existing duplicate at a third cached index. Spy on upsert: exactly one invocation per successful chunk. Assert actual row identities/indices, displaced chunk invalidation, loaded states for chunks without holes, and settled chunk promises. Include duplicates across two incoming chunks; the last processed copy should remain and the chunk losing its record should stay invalidated.
2. Keep comment counts pending with a deferred promise. Assert rows are cached and chunk promises settle while comments remain pending. Resolve counts, flush microtasks, assert the corresponding cached row object exposes the count and `TRIGGER_RE_RENDER` fires; verify a canvas repaint handler can observe it. Repeat with immediate resolved counts and rejected counts. Public/no-permission routes should still skip enrichment and show rows.
3. Replace group cache refs before bulk response completion and assert no rows or placeholder group caches are created, no stale rows enter the enrichment batch, and requests settle. Replace the cache or evict a row after the first commit but before comments resolve; ensure comments do not resurrect rows or overwrite the replacement cache. Include cancelled batches and missing/malformed chunk payloads alongside successful siblings.
4. Document root/search out-of-order response behavior as a separate concern: this guard does not make a root request stale. A broader generation/cancellation fix needs its own controlled overlapping-request test; do not describe this narrow patch as fixing that race.
